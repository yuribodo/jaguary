# BE-09 — Yuno sandbox adapter foundation

## Status of this slice

This slice implements only the safe, testable foundation for Yuno payments. It does not complete BE-09, enable the executor in the composition root, or perform enrollment, queries, or payments in the sandbox.

The fake executor remains the application's only runtime selection. Tests exercise the Yuno adapter with injected `fetch` and credential resolution and make no network calls.

## Configuration

`loadEnv` exposes a discriminated `env.yuno` configuration:

- without `YUNO_ENABLED`, the result is `{ enabled: false }`;
- `YUNO_ENABLED=true` requires `YUNO_BASE_URL`, `YUNO_ACCOUNT_ID`, `YUNO_PUBLIC_API_KEY`, `YUNO_PRIVATE_SECRET_KEY`, `YUNO_COUNTRY`, and `YUNO_REQUEST_TIMEOUT_MS`;
- this phase accepts only the `https://api-sandbox.y.uno` origin, with no path, query, embedded credentials, or alternative port;
- the account ID must be a UUID, country must be two uppercase letters, and timeout must be between 1 and 59,000 ms;
- configuration errors report only field names and rules, never values.

`.env.example` lists names only. Keys and account IDs must come from a secret manager and must never be sent through chat, commits, logs, or fixtures.

## Executor boundary

`YunoPaymentExecutor` implements `PaymentExecutor v1`. Its only economic input is `AuthorizedPayment`; the second argument is exclusively the idempotency key.

| Yuno field | Trusted source |
| --- | --- |
| `account_id`, country, base URL, and headers | Validated configuration |
| `merchant_order_id` | `bound:` plus the reserved `authorization_id` |
| `merchant_reference` | Reserved `checkout_id` |
| Amount and currency | `reserved_amount` |
| Yuno customer ID and `vaulted_token` | `YunoCredentialResolver`, indexed by logical `credential_id` |
| Workflow and payment method | Adapter constants `DIRECT` and `CARD` |

There are no additional amount, currency, merchant, customer, or credential parameters. The resolver also returns the mapping's account ID; any mismatch with configuration fails before the HTTP call.

The idempotency key must be a UUID and is never generated by the adapter. BE-10 owns generation, persistence, and reuse after restarts.

## Money and results

This slice supports only BRL and USD, both with trusted exponent 2. Conversion starts from integer minor units, constructs decimal digits without binary division, and rejects currencies without a mapping. There is no implicit exchange.

A result becomes `APPROVED` only when the response contains all of the following:

- `status=SUCCEEDED` and `sub_status=APPROVED`;
- a valid payment ID;
- the expected account ID and merchant order;
- an identical currency;
- an amount reconstructed to exactly the same minor units.

Terminal refusals become `DECLINED` with a sanitized allowlisted decline code. Local timeout becomes `TIMEOUT`. A `409`, `5xx`, interrupted connection, non-terminal state, malformed payload, or binding mismatch becomes `UNKNOWN`. Operational `4xx` responses reject with a sanitized `YunoAdapterError`.

`TIMEOUT` and `UNKNOWN` do not authorize another charge; BE-10 reconciliation must keep the attempt pending.

## Sensitive data

The adapter does not log requests, responses, headers, customer mappings, or original exceptions. Errors contain only constant codes and messages and do not attach provider bodies or a `cause`. Tests verify that keys, headers, customer data, `vaulted_token`, network tokens, documents, and `raw_response` never appear in errors.

Yuno fixtures contain only synthetic IDs, economic bindings, states, and timestamps. A security test rejects credential material, PII, raw payloads, and PAN-shaped numbers.

## Wiring after BE-10

Wiring must wait until BE-10 persists one Yuno UUID per attempt and supplies it to `PaymentExecutor.pay`. The current store uses `authorization_id`, which is not necessarily a UUID and is therefore rejected by the adapter.

After merging or rebasing BE-10:

1. implement `YunoCredentialResolver` over the adapter's encrypted private storage without exposing mappings to the domain;
2. export the adapter from `backend/src/modules/payments/index.ts` if the composition root uses that barrel;
3. select the executor explicitly in the composition root:

```ts
const paymentExecutor = env.yuno.enabled
  ? new YunoPaymentExecutor(env.yuno, {
      fetch: globalThis.fetch,
      credentialResolver: privateYunoCredentialResolver,
    })
  : new FakePaymentExecutor({
      outcome: "APPROVED",
      occurredAt: clock.now().toISOString(),
    })
```

4. inject `paymentExecutor` into the existing `PaymentService`;
5. never catch a Yuno failure and replace that attempt with fake payment. Selection happens once at startup.

## Remaining external blockers

Before any real sandbox call, the team must:

- obtain explicit user authorization and Test Mode credentials through a secure channel;
- confirm the account, IP allowlist, Yuno Testing Gateway, published CARD route, and Checkout Builder;
- confirm with Yuno that `DIRECT` with `vaulted_token` is eligible and clarify PCI or AOC requirements;
- solve enrollment without exposing a reusable token to application JavaScript;
- implement encrypted credential, customer, and token mapping storage;
- complete BE-10 idempotent persistence, reconciliation, and webhooks;
- select and validate a BRL or USD scenario without currency exchange;
- first perform an authorized, sanitized, read-only query.

No external step above was performed in this slice.
