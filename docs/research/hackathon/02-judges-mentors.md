### Evidence standard

This report separates people who are **explicitly confirmed in public event sources** from people who are merely relevant company representatives or listed as event hosts. It does not claim that a company executive, Luma host, speaker, sponsor employee, or organizer is a judge/mentor unless a source says so.

**Confirmed role terminology:**

- **Judge:** explicitly described as judging the event.
- **Organizer / host:** explicitly described as organizing, co-organizing, or hosting an event city.
- **Mentor:** publicly confirmed only at the group level—Yuno engineers and Nauta experts—unless named by an official source.
- **Relevant representative:** senior organizer/company representative whose perspective could shape the event, but whose judging/mentoring duty is not publicly established.

### Valentina Jordan: likely three-minute-pitch lens

| Pitch element | Likely emphasis | How to address it |
|---|---|---|
| Business story | **Very high.** Is the pain operational, costly, frequent, and real for an operator? | Begin with a concrete workflow failure, affected actor, operational consequence, and baseline metric |
| Technical depth | **High.** Does the agent rely on structured, contextual data rather than generic prompting? | Show source systems/events, canonical data model, retrieval/tool boundaries, confidence and escalation logic |
| UX | **Medium-High.** Does the user know what happened and what action to take? | Show an operator-facing exception/action screen, not a chat transcript alone |
| Innovation | **High.** Is the solution a real operating model rather than a standard dashboard? | Make the new decision/action loop explicit and quantify what it replaces |
| AI | **High, but only if data-grounded.** | Describe why an agent is needed, what tools it can use, what it cannot do, and why context matters |
| Market potential | **High.** Can a mid-market global-trade, importer, distributor, or adjacent buyer adopt it? | Identify the buyer, data-access requirements, rollout wedge, and expansion path |
| Integration | **Very high.** Nauta’s thesis begins with fragmented operational systems | Make ERP/TMS/WMS/email/document/payment connectors and data lineage visually explicit |

## Mentor Strategy

### Questions for Nauta mentors

1. **What specific operational data sources can we access or simulate, and what canonical entities does Nauta consider essential—SKU, shipment, supplier, purchase order, invoice, payment, exception?** This can change the data model and integration scope.
2. **Which Nauta agent/workflow patterns have produced the clearest customer value: monitoring, prediction, investigation, recommendation, or action execution?** This can determine whether to build a copilot, a workflow agent, or a closed-loop agent.
3. **What is the minimum evidence a Nauta user needs before trusting an agent recommendation or action?** This can change the explainability, citation, approval, and audit-log design.
4. **Where do current global-trade operators lose the most time or money because data is fragmented across email, ERP, TMS/WMS, documents, and financial systems?** This can change the chosen problem wedge.
5. **Which trade/payment exceptions are still managed manually today despite existing software?** This can reveal white space beyond inventory visibility.
6. **Should our agent act autonomously in low-risk cases, propose actions for approval, or only investigate? What risk categories require human review?** This can change the product’s safety model.
7. **For a 24-hour prototype, would you rather see one deep workflow with realistic data lineage or a broad multi-agent platform?** This can prevent scope failure.
8. **What would make a payments-related solution feel genuinely Nauta-native rather than merely a payment dashboard?** This can change the integration narrative.

### Questions for Yuno mentors

1. **Which payment event types, failure reasons, and operational signals are most valuable for a prototype—authorization declines, latency, retries, fraud signals, fee anomalies, payout failures, settlements, chargebacks, or reconciliation mismatches?** This can change the prototype’s core event model.
2. **Which Yuno APIs, SDKs, webhooks, sandbox credentials, and sample data are available today, and which integration is most credible to demo?** This determines whether to build against real or simulated interfaces.
3. **What payment problem currently creates the highest merchant pain: conversion loss, provider outages, routing, local methods, payment recovery, fraud false positives, cost allocation, payout operations, or reconciliation?** This changes opportunity prioritization.
4. **What agent actions would Yuno consider safe enough to automate versus require merchant approval?** This changes policy, governance, and UX design.
5. **How should a prototype demonstrate correct payment engineering—idempotency, webhook verification, state transitions, retries, PCI/PII minimization, auditability, rollback?** This changes technical acceptance criteria.
6. **Which buyer/persona should we optimize for: payment operations, engineering, finance, risk, merchant support, banks, or a marketplace?** This changes the demo and economic narrative.
7. **Is a Yuno integration mandatory, preferred, or optional for the challenge? If required, what exact capabilities should a winning team demonstrate?** This can invalidate or validate the product direction.
8. **What does Yuno view as the most promising role for AI in payment orchestration over the next year?** This can change the agent’s scope.

### Questions for technical mentors

1. **What is the event’s official required submission artifact: repository, deployment, API docs, video, slides, demo credentials, architecture diagram, or all of these?** This changes execution planning immediately.
2. **Are there sandbox constraints, rate limits, authentication rules, prebuilt SDKs, webhook endpoints, API quotas, or required observability tools?** This changes architecture.
3. **Can we use mocks/synthetic data for payment, logistics, and agent actions, and how should we label them in the demo?** This changes feasibility and claims discipline.
4. **What quality bar separates a functional prototype from a concept?** This changes the allocation between frontend polish, backend reliability, and data realism.
5. **Are there preferences or requirements for public GitHub, open-source licensing, cloud deployment, or data privacy?** This changes repository and infrastructure decisions.
6. **What failure-mode demo would signal technical maturity: provider outage, payment decline, missing document, duplicate event, low-confidence AI decision, or policy violation?** This can shape the standout demo moment.

### Questions for product/business mentors

1. **Which challenge outcome is weighted most heavily: innovation, technical execution, business impact, AI quality, integration, UX, or pitch?** This determines the final build-versus-story tradeoff.
2. **Who is the primary buyer and user expected by the challenge brief, and what budget or operational KPI would justify adoption?** This changes the business model and pitch.
3. **What differentiates a winning solution from an internal tool or generic feature request?** This can sharpen the category and moat.
4. **Would a narrow high-value workflow be scored better than a broader platform vision?** This changes scope.
5. **What evidence of market demand is persuasive in the final pitch: customer quotes, market size, time saved, revenue recovered, pilot design, integration commitments, or unit economics?** This changes research and pitch preparation.
6. **What should teams avoid in terms of unsupported claims, compliance risk, autonomous decision-making, or unclear ownership?** This can prevent avoidable judge objections.
